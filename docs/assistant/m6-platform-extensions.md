## Implemented companion paths

- The web Assistant now has an accessible, expandable feature guide based on the current local voice check. It distinguishes typed preview, microphone permission, installed speech playback and unsupported phone effects. Opening the guide requests no permission and executes no command. Existing authenticated, consented public-test AI planning stays unchanged.
- iPhone has a matching feature guide and optional foreground English speech bridge. Both microphone and Speech authorization follow an explicit microphone gesture and session consent. Native recognition requires `supportsOnDeviceRecognition` and sets `requiresOnDeviceRecognition`; no cloud recognizer or automatic model download is provided. Missing native code, denied permissions and unavailable local English keep typed commands usable. Thirty-second native bounds, request IDs, cleanup on background/protected-data loss/audio interruption and suppression of late callbacks protect the session. Playback uses an installed English system voice and starts only on request.
- An iOS 17+ **Create event in Apple Calendar** entry opens Apple's native event editor. The user enters the private title/time and chooses Save or Cancel there. Contexify neither reads existing events/calendars nor directly saves or caches these details, sends them to Gemini, or adds them to its account storage. Save is described as an editor report, not a verified future alert. Apple's calendar selection may sync the event through the user's Apple account; it is managed there and is not deleted by Contexify sign-out.
- An iOS 17+ Siri/App Shortcuts entry opens Assistant after local device authentication. It carries no text, starts no microphone and approves no effect. An in-memory, one-use entry expires after thirty seconds; cold/warm launch and app activation use the same consumption path. App-target metadata includes the native module's App Intents package. This is a Siri invocation, not a Contexify background wake-word listener.
- Existing Android effects remain unchanged. The reminder claim contract now distinguishes `ios_owned_schedule` from `android_owned_reminder`; only the owned-reminder scope accepts an enrolled iOS device. Volume, brightness, app-opening and Android Clock scopes still reject iOS. New Apple APIs are optional bridge discovery; old binaries continue to use text/preview and manual Calendar access. Existing reminder routes, tables and encrypted account-copy logic are reused; no new route/table, provider request, third-party dependency or Android native change is introduced.

The Calendar entry is a user-composed OS editor, not an AI-issued execution adapter. There is no model action or server permit to turn into a write: all new event details and the Save decision stay in Apple's editor. Do not wire it into the command planner or describe it as one-use server-authorized execution without a separately reviewed adapter. Existing Android planner/policy/proof/claim/receipt controls remain in force.

## Owned iOS scheduling architecture

`AppleScheduleController` shares the existing security module's nonexportable device key and installation/account/origin binding. It obtains an owned-reminder scoped session and checks `/operations/identity` online before decrypting private state. Fresh authority is required for create/cancel/read/account-copy operations. The existing opaque commitment, immutable operation identity, exact native approval, signed authorization, atomically consumed one-use claim and signed receipt remain separate stages. iOS cannot claim an Android control or handoff. No general-purpose signer or model executor is exposed.

Native drafts validate title/control characters, real calendar dates, selected IANA zone, explicit DST gap/fold handling, a one-minute minimum, ninety-day horizon and bounded daily/weekly repetition. A timer accepts 60-86400 whole seconds and begins after approval/claim. At most 32 pending owned occurrences are supported; recurring alerts use a finite approved list of UTC instants, so phone display-zone changes do not rewrite authority. This limit and OS registration capacity may reject a longer schedule. Do not silently shorten it. Server quotas can also reject rapid tests; stop on a quota response rather than repeatedly retrying.

Notification reminders use one-shot `UNUserNotificationCenter` registrations with generic locked-screen text. AlarmKit uses fixed-date ringing alarms or its actual countdown-timer configuration. Ringing may override Focus/silent mode; permission and native approval disclose this. Timer presentation has a WidgetKit/ActivityKit extension with generic content and opaque metadata, no account, tokens, private title, app group or network port. Standard system Stop controls can end an already-approved alarm offline; stopping is not new scheduling authority. Application-generated cancel requests use the signed online flow.

The app reads back its own OS registration IDs, without treating registration as proof of delivery, ringing or hearing. Missing registrations and interrupted requests remain unknown. Before a potentially ambiguous claim, encrypted state is written as `schedule_unknown`; there is no automatic effect replay after restart, response loss, key loss, permission denial or a background interruption. Partial registrations are removed using only that request's IDs. A failed cleanup leaves uncertainty rather than declaring success. User cancellation can remove an unknown registration. Timer requested deadlines in the list are descriptive; system pause/stop changes are not inferred as verified delivery.

Private bodies and metadata use AES-GCM with a Keychain `WhenUnlockedThisDeviceOnly`, non-synchronizing key. The protected file/directory are excluded from backup. Authenticated account/origin changes, sign-out and device forgetting cancel only Contexify-owned pending/delivered notifications and AlarmKit client registrations, then erase local details. Apple's Clock/Calendar and other apps remain separate. A durable generic cleanup tombstone survives interruption, including an in-flight scheduling race. New scheduling remains blocked until cleanup is checked; missing/invalid encrypted state cannot silently adopt old registrations. Remote revocation can be observed only when the phone reconnects and checks authority; already-approved alerts can work offline.

Notification reminders reuse the existing explicit encrypted account-storage toggle, revision checks, save/list/delete APIs and draft-only recovery. Details reach the configured Contexify backend only after that opt-in, not Gemini. Restored copies never automatically schedule. AlarmKit alarms/timers are device-only in this flow; their private typed payloads are never sent as account copies. Local history is cleaned on foreground access after seven days beyond the last requested occurrence. There is no background private-data reader or rescheduling worker.

The native source policy suite is available on a Mac with `swift test --package-path mobile/modules/assistant-device-security`. It tests real Swift date/zone/DST/capacity/title/strict-protocol behavior using fixed synthetic dates. It has **not run on this Windows host** and is part of B1. `#if canImport(AlarmKit)` / runtime iOS checks and weak framework linkage protect older supported iOS versions. The app/widget require the current SDK for compilation. The plugin creates and embeds the widget idempotently and inherits the app's signing team/version; it never selects a real team, accepts an agreement or spends cloud-build credits.
