# Capability permissions and authorization

Proposed policy, 2026-11-07. Platform evidence: [feasibility](feasibility.md). Enforcement protocol: [architecture](architecture.md). These are future requirements, not permissions already held by Contexify.

## Common rules

Four separate checks are mandatory: account/device authority, granular product consent, current OS permission, and current user intent. None substitutes for another. Default deny unknown capabilities, unsupported OS/API versions, guests, disabled flags, revoked devices and stale policy. Ask for permissions just in time with purpose and local/cloud disclosure; denial preserves text/chat functionality. Never ask for all permissions during onboarding.

Risk classes: **R0** nonprivate reads; **R1** bounded, reversible, local changes; **R2** private data access, scheduling or destructive local changes; **R3** communication, disclosure or external-account effects; **prohibited** uncontrolled or security-bypassing operations. A capability's risk can increase with arguments/context and never decrease at the model's request. Reading aloud private data is disclosure even though the database operation is a read.

Confirmation policies: **C0** deliberate foreground instruction suffices after checks; **C1** editable preview and deliberate approval for the specific action; **C2** exact transaction preview plus explicit approval, with device authentication for new recipients/integrations, unusual destinations, stale authentication or other high-risk context. R2 private reads require a scoped user request and unlock, plus C1 for cloud transmission/read-aloud. R3 never accepts an ambient spoken “yes” as sole confirmation. Locked-device actions are deferred to unlock in MVP; Siri/Shortcut invocation is not a confirmation bypass.

## Capability catalog

Every entry inherits account/device binding, strict schema validation, bounded timeout, safe error wording and audit/revocation rules below. Availability is computed on the device and rechecked immediately before dispatch. Platform abbreviations: W web, A Android, I iOS.

## Results, failures, audit and revocation

| Capability family | Verifiable success and failure handling | Minimal audit | Revocation behavior |
| --- | --- | --- | --- |
| Capture / TTS | Recording state/stop callback; transcription may fail or be uncertain; text fallback. TTS callback means audio emitted, not heard | Start/stop reason, duration bucket, processing mode; no audio/transcript | Stop immediately; release audio resources; clear buffers and cloud streams |
| Owned reminders/alarms | Persist ID + OS registration/readback where available. At fire time “delivered” only with observable evidence. No callback means delivery unknown | ID, intended time, schedule/reconciliation state; private title encrypted locally | Deny new mutations; invalidate approvals; show cancellation option and reconcile OS schedules. Already scheduled alarms may persist until explicitly removed |
| Clock/editor handoff | Intent/controller opened; saved/completed only with a documented reliable result; missing handler or cancellation remains explicit | Handoff target ID, attempt, callback class | Stop pending dispatch. Revocation cannot undo an action completed in another app |
| Private read/contact/calendar | Returned authorized records, not assumptions; handle limited access, deleted contacts and changed calendars; ask again for collisions | Scope/range/count, not names/numbers/events | Stop queries, clear transient selections and sensitive cached data; refresh grants before next read |
| Call/SMS/WhatsApp composers | `handed_off`; Apple “sent” callback may support `submitted`, never delivery. No blind retry after dispatch or return | Capability, random action ID, confirmed revision/digest, status; encrypted local display summary | Invalidate pending actions; delete drafts held by Contexify. Other app's draft or sent content is outside Contexify's deletion control |
| Volume/brightness | Read back supported state; quantization/routing may change achieved value. Bound one set and one verification read | Requested/achieved numeric value and scope; no private content | Deny new changes; optionally restore captured app-scoped setting if still owned and user has not changed it |
| App/settings opener | OS accepted open; no claim about app's internal state | Catalog ID, handler outcome | Deny pending opens; cannot force-close or undo another app |
| Future direct/provider action | Provider operation ID plus strongest documented receipt. Network timeout after submission -> outcome_unknown; query state, never resend automatically | Receipt ID, state, digest, policy version; encrypted minimal metadata | Revoke connector tokens and new permits; preserve necessary redacted evidence; remote completed effects remain |

Global audit envelope: random action/attempt IDs, pseudonymous account/device references, capability/schema/policy version, consent version, time, confirmation method, prior/new state, safe error code and proof digest. Never log tokens, full destination, message body, raw calendar/contacts/audio or provider response bodies. User-visible private history is separately encrypted and access-controlled; an audit hash must not be used to claim nonrepudiation or hide plaintext retention.

All denials have typed reasons (`permission_denied`, `permission_revoked`, `device_locked`, `auth_expired`, `unsupported`, `ambiguous`, `cancelled`, `deadline_exceeded`, `outcome_unknown`). Re-request a denied OS permission only after a fresh user gesture; show settings guidance for permanently denied states. Do not repeatedly prompt or silently select a weaker/cloud permission.

Consent is scoped by account, device, capability family, processing destination and policy version, with independent toggles for wake word, microphone, cloud STT, cloud planning, private-data summaries and each connector. Withdrawal invalidates outstanding permits and queued proposals. A different recipient, content, schedule, device or plan revision always needs a new confirmation. Batch approval never grants blanket permission for future actions.
