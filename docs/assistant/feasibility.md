# Device assistant feasibility

2026-11-12 update: the repository observations below describe the planning baseline. Phase 1A has since added secure credential storage and a native device-key module; see [implementation and verification limits](phase-1a-security.md). Voice, task execution and platform capability claims remain gated as described here.

Planning proposal, 2026-11-07. Source baseline and confidence labels: [review coverage](review-coverage.md). No assistant implementation exists in this change. Official documentation establishes API possibilities, not that Contexify has passed device tests or store review.

## Recommendation and existing foundation

Keep FastAPI, React/Vite and Expo/React Native. Ship a foreground, push-to-talk assistant first, initially on Android with a restricted web companion. Add iOS through the same Expo app after native adapter validation. Start with Contexify reminders and bounded display/audio controls; defer communication actions and background wake words. Native integration is required, but a separate Kotlin/Swift application rewrite is not.

Verified source: `mobile/package.json` declares Expo ~58.0.19, React Native 0.88.0 and React 19.3.0; `mobile/app.json` configures Android and iOS and EAS Update. No tracked native `android/` or `ios/` project, speech capture/recognition, wake engine, notification scheduler, device key, or action registry was found. This is an existing native application implemented with React Native, not merely a website wrapper. Installed/released binaries and entitlements were not inspected. Web has a manifest but no tracked service-worker registration or offline scheduling implementation.

Expo's [Modules API](https://docs.expo.dev/modules/overview/) supports Kotlin/Swift adapters. Use development builds for new modules; Expo Go cannot validate an arbitrary new native adapter. Native permissions, services, App Intents and binaries must be built and distributed. With the current `appVersion` runtime policy, update the runtime/app version for native changes; an OTA bundle alone cannot add native capabilities. [Expo runtime versions](https://docs.expo.dev/eas-update/runtime-versions/).

## Platform matrix

**Native** = official API within its scope; **handoff** = user completes action in another app; **conditional** = availability/permission/version/provider dependent; **no** = no supported general-purpose privilege for this design. All rows describe proposed support, not implemented behavior.

| Capability | Web / PWA | Android native | iOS native | Verification boundary |
| --- | --- | --- | --- | --- |
| Push-to-talk | Conditional: secure-context microphone; browser ASR or opted-in cloud | Native recorder + on-device recognizer when available | Native recorder + supported on-device Speech | Transcription is untrusted and editable; no action from partial transcripts |
| Local TTS | Browser/voice dependent | Installed system voice; reject network voice in local mode | System synthesis with tested voice | Speaking a response proves no device action |
| Custom wake word while visible | Possible with permission and local engine; tab lifecycle limits | Feasible experiment | Feasible experiment while recording is permitted | False triggers cannot authorize actions |
| Custom wake word asleep/background | No dependable cross-browser service | Conditional selected assistant service, or user-started microphone foreground service; OEM/hardware limits | No general third-party always-on assistant entitlement established | Never promise all-day listening across platforms |
| Contexify reminder create/list/cancel | App records; foreground alerts; optional later best-effort Web Push | App-owned local notifications, permission and timing limits | App-owned local notifications, permission and timing limits | Scheduled/registered differs from delivered or heard |

| Cancel next alarm | Own records only | Own alarms; Clock dismiss intent where handled, with user selection | Own AlarmKit alarms; no general access to Apple's Clock database | Resolve exact target; never silently cancel every alarm |

The browser microphone API is permission-controlled and requires a secure context. A PWA installation does not grant OS-level execution authority. Service workers are event-driven and may terminate; they are unsuitable for an always-running microphone or precise local alarm. [W3C media capture](https://www.w3.org/TR/mediacapture-streams/), [W3C service workers](https://www.w3.org/TR/service-workers/). iOS Home Screen Web Push is available from iOS/iPadOS 16.4, subject to permission and installation conditions; it remains a delivery channel, not an exact-alarm guarantee. [WebKit](https://webkit.org/blog/13878/).

## Native constraints that affect scope

Android's user-selected `VoiceInteractionService` is kept running for voice interaction. This does not confer every protected permission or guarantee a custom hotword can use a device's low-power DSP. Hardware, enrolled models, OEM behavior and public API availability must be tested; automotive/OEM documentation is not proof of ordinary Play-app privileges. Require `BIND_VOICE_INTERACTION` on the service and explicit user role selection. [VoiceInteractionService](https://developer.android.com/reference/android/service/voice/VoiceInteractionService).

For ordinary apps, Android 12+ restricts background foreground-service starts; Android 14+ checks while-in-use microphone access when creating such a service. A permitted user-started recording service needs the appropriate microphone service type, permissions, visible notification and stop control. Test screen-off, battery saver, process death and reboot. Do not blanket-request battery exemption or restart recording after reboot. [Foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

Clock intents and app-owned alarms are different designs. Prefer Clock UI handoff for an early alarm experiment. App-owned exact alarms require evaluating `SCHEDULE_EXACT_ALARM` special access versus the restricted `USE_EXACT_ALARM` use case, checking access, rescheduling owned alarms after reboot, and handling revocation. Do not call an inexact reminder an exact alarm. [Common intents](https://developer.android.com/guide/components/intents-common), [AlarmClock](https://developer.android.com/reference/android/provider/AlarmClock), [AlarmManager scheduling](https://developer.android.com/develop/background-work/services/alarms).

Apple's AlarmKit supports app-owned alarms and timers with authorization and `NSAlarmKitUsageDescription`; it does not expose arbitrary Clock alarms. Availability starts with iOS 26 and must be checked at runtime. [AlarmKit](https://developer.apple.com/documentation/alarmkit), [scheduling sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit), [Apple developer relations availability clarification](https://developer.apple.com/forums/thread/794730). App Intents expose Contexify's declared actions to Siri/Shortcuts; they do not grant unrestricted control over other apps. [App Intents](https://developer.apple.com/documentation/AppIntents). Background audio modes must serve their declared purpose; do not disguise perpetual assistant listening as audio playback or VoIP. [Apple review rules 2.5.4 and 2.5.14](https://developer.apple.com/app-store/review/guidelines/#software-requirements).

Prefer dial and message composers without direct call/SMS permissions. Google Play restricts SMS/call-log permissions to eligible roles or approved exceptions; becoming default assistant is not automatic approval. [Play permission policy](https://support.google.com/googleplay/android-developer/answer/10208820). Apple's [message composer](https://developer.apple.com/documentation/messageui/mfmessagecomposeviewcontroller) requires user action and does not guarantee delivery. WhatsApp's [click-to-chat](https://faq.whatsapp.com/5913398998672934) opens a prefilled draft. Business Platform is a separate integration with business sender identity, credentials, policies and commercial review, not automation of a user's personal account. [Meta's maintained Cloud API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api).

Use the least calendar access needed: iOS event editor for user-driven creation, write-only for direct creation, full access for reads, and separate Reminders access. [EventKit access](https://developer.apple.com/documentation/eventkit/accessing-the-event-store). Android global brightness needs Settings write approval; window brightness does not need that global grant. [Settings.System](https://developer.android.com/reference/android/provider/Settings.System). Android media volume respects route/fixed-volume restrictions; avoid ringer/DND changes. [AudioManager](https://developer.android.com/reference/android/media/AudioManager). iOS system volume is exposed through user UI, while [screen brightness](https://developer.apple.com/documentation/uikit/uiscreen/brightness) has its own API. [Apple outputVolume guidance](https://developer.apple.com/documentation/avfaudio/avaudiosession/outputvolume).

## Voice technology decision

| Option | Privacy/offline and cost | Accuracy/latency/maintenance tradeoff | Recommendation |
| --- | --- | --- | --- |
| Android SpeechRecognizer / Apple Speech | Request verified on-device mode; availability varies by locale/model/device; no Contexify per-minute API charge | Low integration burden; installed language models, interruptions and OEM quality vary | First native implementation; fail visibly to text when local mode unavailable |
| Browser SpeechRecognition | Some implementations transmit audio; local-processing support is conditional | Browser and language coverage differs; background unreliable | Explicit feature detection and disclosure; no silent cloud fallback |
| Managed cloud STT | Audio leaves device; metered; region/retention contract required | Consistent API, network latency, broader language evaluation | Optional opt-in fallback after provider review; not default always-on audio |
| Bundled offline ASR model | No inference API fees; larger app/download and compute | More engineering, memory/battery and Hindi/Hinglish evaluation | Benchmark only if native coverage fails product needs |
| Native/browser TTS | Local only with an appropriate installed voice and verified engine | Small dependency footprint; differing voices/languages | Default; text fallback and mute/interrupt control |
| Cloud TTS | Text disclosure plus metered latency | Voice quality may improve | Deferred; no private schedules/messages sent merely to improve voice |

Android SpeechRecognizer explicitly is not a continuous-listening wake engine; on-device availability must be checked. [Android recognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer). Apple requires both supported local recognition and `requiresOnDeviceRecognition`; otherwise do not claim offline processing. [Apple local recognition](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition). Browser local recognition is evolving: [Web Speech proposal](https://github.com/WebAudio/web-speech-api/blob/main/explainers/on-device-speech-recognition.md), [Edge implementation](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/speech-recognition-api). TTS adapters use [Android TextToSpeech](https://developer.android.com/reference/android/speech/tts/TextToSpeech) and [Apple AVSpeechSynthesizer](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer).

Wake-word candidates: Porcupine offers local custom phrase detection and mobile SDKs, but AccessKey handling, licensing, telemetry and commercial offline behavior need written verification; a shipped client cannot keep an embedded reusable vendor secret confidential. Do not select it until provisioning satisfies the no-hardcoded-secret requirement. [Porcupine Android](https://picovoice.ai/quick-start/wake-word-android/). openWakeWord is a possible research baseline; its upstream pre-trained models have noncommercial licensing and currently focus on English, so they are unsuitable as an unexamined commercial dependency. Custom licensed training data and mobile runtime work would be necessary. [Upstream project](https://github.com/dscripka/openWakeWord).

Proposed recording lifecycle: explicit activation -> visible listening -> bounded utterance (30 seconds maximum) -> stop audio -> editable transcript -> plan -> confirmation -> verified result -> optional TTS. Cancel/lock/background/permission loss ends capture; a later wake experiment has its own documented foreground/background policy. Suppress wake detection during TTS, implement audio-focus interruptions and headset route changes, and never treat a voiceprint or wake phrase as authentication. English first is an estimate assumption; Hindi/Hinglish requires its own corpus and approval.

## Outstanding feasibility evidence

No physical phone, browser microphone, recognizer, AlarmKit, Clock intent, store entitlement, provider account or battery benchmark was exercised. Minimum OS versions must be pinned against the installed Expo SDK and actual binary targets. Every conditional row stays disabled until its adapter passes [release gates](testing-strategy.md). Current provider model strings are repository configuration, not verified availability. See [costs and approval decisions](implementation-plan.md).
