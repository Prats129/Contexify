## Implemented behavior

- A single reviewed `brightness.set_app` action accepts integer percentages **10–100**. The signed-in Android assistant UI provides device setup and **Confirm app brightness change**. Multi-step proposals cannot silently execute one selected part. Voice/text still produce a review; exact native approval is required for every effect.
- Only Contexify's current Activity window is changed through public `Window.attributes.screenBrightness`. No `Settings.System` writes or `WRITE_SETTINGS` permission are introduced. System brightness, other apps, volume and alarms are not brightness targets. [Android window-brightness contract](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#screenBrightness), [window attributes](https://developer.android.com/reference/android/view/Window#setAttributes(android.view.WindowManager.LayoutParams)).
- The native adapter remembers the prior value for each live window in memory and keeps it across changes while it still owns the current setting. If another owner changes brightness before a later assistant request, that newer value becomes the restoration target. Background/destroy/key deletion restores the owned setting, including Android's `-1` system-default sentinel. Restoration does not overwrite a different value applied since the last assistant action. Window references are weakly held for saved overrides; no original setting is added to backups or replayed on restart. Pending confirmation is bound to the reviewed window, foreground/resumed activity, passcode/unlock state, identity and expiry.
- Readback verifies the **window attribute**, not measured panel luminance. Brightness evidence uses 10,000 fixed units with exact requested-percent agreement; audio-stream units cannot substitute for window evidence. UI and confirmation identify the limited scope and background restoration.

## Shared security and compatibility

The existing volume protocol is extracted into `PercentControl`, configured only for the compiled `volume` and `brightness` modes. SQL table identifiers derive from that fixed allowlist; user arguments remain bound SQL values. Volume URLs, scopes, proof purposes, schemas, policy version and v3 data remain compatible. Each scope has separate sessions, task records, challenge purposes and one-use claims. Brightness uses `/api/v1/assistant/brightness`, `assistant:brightness`, `assistant_brightness_*` proof purposes and `android_app_brightness` execution claims. A volume bearer cannot authorize brightness or vice versa.

Schema migration **v4** adds brightness session/task tables and indexes. The prior v3 DDL is unchanged behind its helper; repeated migration, rollback and fixture restore checks cover the additive upgrade. No migration was run against configured production or the running practice database during this task.

The native `PercentControlExecutor` shares HTTPS validation, exact confirmation, proof binding, expiry/lifecycle guards, atomic replay journals and truthful outcomes. Compiled `MediaVolumeControl` and `AppBrightnessControl` adapters own their effects. Existing volume readback/rounding and safe-volume/DND behavior are retained. A shared native running guard and shared JS operation guard prevent simultaneous volume/brightness requests. Cancellation covers both pending executors; lifecycle reset additionally restores brightness. Journal files use separate mode namespaces; uncertain work is never automatically repeated.

Both controls reuse device enrollment and the existing shared server/native execution gate. **No brightness-specific environment switch** is added. Production defaults stay off; web and iOS remain previews. New optional native bridge methods reject unsupported older binaries rather than substituting another action. Both clients receive additive brightness wire declarations; existing generated declarations are preserved.
