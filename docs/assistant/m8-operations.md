## Implemented operational safeguards

`assistant_artifact.py` supplies the version/name for preparation, copying and inspection. This closes the old launcher mismatch that copied code-7 output under the code-6 filename while inspecting a different existing file. The launcher also includes the M7 native policy tests.

Before assembly the launcher records a bounded source fingerprint of mobile/core code, native module/plugin inputs, dependency locks, static assets and prepared native Android inputs. Generated build outputs, package installations, dotenv, database state and private keys are excluded. Inspection rechecks the source snapshot and hashes the copied APK against the actual current build output before and after inspecting it. If either changes, delivery fails. The report records whether this boundary proof exists; an old artifact inspected without a prebuild snapshot is not retroactively granted one.

These are local source-boundary checks, not a signed hermetic build attestation. Compiler provenance, dependency/license/SBOM review, independent assessment and signed distribution still need their own release evidence. No APK rebuild or repeat phone testing is required just for these tooling changes; the user-tested M7 binary is unchanged. Use the new path when a native change genuinely requires a new binary.

`assistant_release_check.py` reads the versioned `release-evidence.json`, checks required A-F entries, reviewer/reference completeness, target-specific device evidence, exact artifact hash, inspection safety fields and current source proof. It emits only gate IDs/states, artifact digests and fixed reason codes, never command/recipient/audio/credential content. Invalid evidence exits 2; a hold exits 1; complete supplied evidence exits 0. Every report says `runtime_authority: none`. It neither changes configuration nor deploys, issues execution permits or authenticates a reviewer. Gate claims must be reviewed through the normal project review/operations process.

Android test-package/custom-CA artifacts cannot qualify for public distribution. The current report must remain on hold. iPhone and deployed-web verification cannot be inferred from the Android inspector and remain explicit blockers for their respective targets. Optional wake being disabled does not block unrelated non-wake work; enabling it requires an approved D7 decision plus applicable gates.

## Containment, recovery and rollback runbook

1. **Contain new authority.** An authorized operator disables the existing shared backend execution/planning gates and restarts the affected service through the deployment's reviewed configuration process. Keep security management available where needed for authenticated device/session revocation. This document performs none of these actions. No per-command switch is introduced.
2. **Respect outstanding authority.** In-flight provider traffic cannot be retracted. Already issued/claimed authority has its existing expiry/lifecycle bounds; stopping the server is not proof every phone effect stopped. Approved offline notifications and external Clock alarms, Phone/SMS composers or saved drafts have their own ownership/revocation limits. Do not claim cancellation, deletion or undo without evidence.
3. **Revoke and preserve.** Use existing authenticated device/session management. Preserve minimal operation IDs, revisions and evidence; redact commands, contacts, message text, audio, credentials and provider error bodies. Fleet-wide operator roles/procedures and log retention require the remaining governance review; do not invent an unauthenticated admin endpoint.
4. **Reconcile without replay.** Read supported status/evidence only; retain `outcome_unknown` if the effect cannot be established. Do not retry an uncertain write or turn write gates back on just to inspect state. Exact transaction confirmation remains required for any new request.
5. **Restore in isolation first.** Prove consistent backup/restore, key availability/rotation, ownership, revocation tombstones, migrations and already-applied/unknown effects on a disposable copy before any configured database change. Restoring an old auth/permit/task database can resurrect authority or erase duplicate-prevention evidence. Keep gates off and require reviewed session/device/authority invalidation and reconciliation before serving restored state. SQLite/Turso and device/OS schedules need separate evidence.
6. **Roll forward safely.** Do not uninstall the phone app or force a lower Android version code to “roll back”; that can lose local keys/reminders or fail installation. Keep authority disabled and prepare a tested forward-fix with a higher version code, the same approved identity/signing key and compatible data handling. Backend rollback must preserve schema/ledger/revocation semantics. Distribution and production changes require approval after the concrete artifact is reviewed.
