# M4: stable settings operations and recovery

Date: 2026-11-18. Scope: source implementation for the existing Android settings executors. M2/M3 live and phone acceptance remains open in [Android acceptance](android-acceptance.md). This batch does not authorize production enablement, new provider processing, a cloud build or phone access.

## What changed

An AI settings proposal now retains its validated plan ID, immutable revision and ordered dependencies through the command session and the new native `executePlanV2` bridge. A clarified volume action uses revision 2 of its question's plan and retains its required local context ID. It cannot fall back to an absolute write. Editing/submitting a deliberately new command obtains a new planning identity; duplicate callbacks, taps and dispatches of one reviewed snapshot retain the original identity. The session consumes that review once.

The native coordinator accepts at most five steps. Step IDs are their stable indexes, with unique backward-only dependencies. It validates the whole graph and every compiled handler, policy range and current device readiness before starting. Media volume and Contexify app-window brightness are supported; a graph containing an app-open or another unsupported action remains a whole-plan preview. No supported first half is silently executed. Relative app brightness still requires an exact preview; no new system-brightness permission or context reader is introduced.

Native execution is serialized across plans, recovery and the retained legacy controls. Every step still needs its own exact native confirmation, current binding, foreground/unlocked checks, existing online authorization and atomic single-use claim. Native memory reuses the plan's capability-scoped sessions. A failed, cancelled, unknown or locally verified result without a recorded server receipt stops **all** remaining steps, including independent ones. There is no automatic resume, rollback, recomputation or offline dispatch. A native exception returns the matching available checkpoint conservatively; it does not create a new operation.

## Stable server identity without a second task ledger

The additive `/volume/operations` and `/brightness/operations` routes derive the existing idempotency key from `(plan_id, plan_revision, step_id)`. The existing task tables already bind that key to account/device and immutable arguments. The existing signed native task confirmation, permits, claims and receipts remain authoritative. The v2 bridge coordinates those v1 task transactions; it does not alter their signed envelope or weaken their session isolation.

`/operations/status` is an authenticated, rate-limited read-only projection for a known v2 identity on the same account/device. A newly authenticated device scope may read its earlier v2 evidence, but cannot authorize, claim or resume the earlier task. The original v1 task lookup still requires its original scoped session. Missing/other-device evidence returns 404; expired/revoked authority is denied. Claimed/in-flight work projects `outcome_unknown`; pending expiry projects `expired`, with **no task UPDATE**. A status response contains no new permit or execution authority. The additive `/operations/identity` read validates the current server-side parent/device scope against the native origin, account, installation and public key before native code reserves a plan or decrypts recovery records. A saved profile/marker alone cannot read the history; revoked or mismatched authority fails before decryption. No SQL migration, extra ledger or new per-command environment flag was needed.

## Encrypted recovery metadata

Before any v2 step can dispatch, the native coordinator commits a minimal checkpoint and then atomically marks that step uncertain. Storage uses Android Keystore AES-256-GCM with fresh IVs and associated data binding installation, account/origin binding and plan filename. The non-exportable app key remains in Keystore; this does not promise hardware backing on every device. Files are in `noBackupFilesDir`, with bounded authenticated reads, explicit fsync, atomic replacement, readback verification and compare-and-swap storage revisions. A process-wide storage lock and an enrollment-marker check serialize forgetting against journal writes, preventing a cancelled worker from recreating a forgotten journal. An existing plan ID cannot be overwritten, even by changing its supplied revision or arguments; a genuinely new command is required. Plan revisions are immutable; checkpoint revisions advance with each transition.

Records contain opaque identity, an immutable plan digest, expiry, capability/target and per-step state/result evidence. They contain no transcript, audio, bearer credential, permit, contacts or raw local-volume reading/context. The plan digest binds its local precondition without storing the context itself. This is action recovery metadata, separate from chat and analytics. V2 does not write the legacy executor's plaintext task journal.

The store is bounded to 512 plan records. Records older than seven days after plan expiry are pruned on a later deliberate plan submission; it is not a background deletion guarantee. Capacity, corruption, unavailable keys and failed durable writes fail closed. Missing keys are never silently replaced over existing recovery files. Ordinary sign-out retains encrypted evidence but cannot access it without the matching signed-in binding; forgetting the device deletes its recovery files/key. Re-enrollment uses a fresh installation identity, with no restored execution authority. Existing v1 journal retention is unchanged. The production D8 retention/rotation/deletion/restore decision and physical key/backup verification remain release gates; this development implementation is the concrete local design to review.

Android's documented pre-15 issues with [`setUnlockedDeviceRequired`](<https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean)>) are avoided for the new AES key by applying that flag only on Android 15+. Native foreground/unlocked checks still apply on all supported versions. Atomic replacement follows [`AtomicFile`](https://developer.android.com/reference/android/util/AtomicFile), with explicit sync and authenticated readback before dispatch. Tests of the portable cipher are not Android Keystore/device proof.

## Recovery and truthful results

**Check previous actions** is deliberately read-only and user initiated. It examines at most three recent saved plans, using local authenticated evidence and, when available, matching authenticated server receipts. Pending steps become “not started” in this projection; unknown results never imply success from the current setting or model text. A locally verified effect without a server acknowledgement remains distinct from a recorded receipt. Recovery does not read AudioManager, recreate tasks, issue approvals/claims/receipts, dispatch writes or mutate the saved checkpoint. Status network failure preserves uncertainty. Recorded results are labeled as historical, rather than current device readings.

The UI shows the control, step, verified/failed/cancelled/unknown result and unstarted remainder. Clear, Close, background and account cancellation suppress late results and stop future work. Context expiry/change still uses M3's native preconditions. An app-window brightness verification remains attribute readback, and the normal background restoration still applies. It does not prove screen luminance or a lasting system change.

This provides at-most-one attempted dispatch per retained identity in this native coordinator, not a universal exactly-once OS effect. A crash/lost claim or unrecorded result remains uncertain. User-created new commands can intentionally repeat an effect after fresh policy/approval; reconciliation never does so automatically. There are no compiled app/communication handoff executors in M4; their truthful handoff/delivery states remain with M5/M7.

## Compatibility and verification boundary

The new bridge is additive. Legacy single local commands retain their existing v1 methods. AI/v2 plans cannot downgrade to those methods on older binaries. Browser/iOS remain previews and cannot execute Android plans or read its recovery store. Generated backend wire types are updated in both clients; the native plan/result contract is shared in `assistant-core`. No application dependency or permission was added. The pinned source formatter is a development-only tool in the ignored cache.

M4 requires a new compatible native binary before manual acceptance; the previously installed code-2 APK cannot acquire these methods through a JavaScript update. No APK/EAS/OTA build, installation, phone access, live Gemini request, backend restart, production deployment or quota increase was performed in this batch. Final automated verification is recorded below; none of it is physical phone acceptance.

Required physical acceptance: per-step native confirmations and cancellation after partial success; duplicate taps and independent concurrent commands; changed/expired relative context; background/lock/logout while steps are pending; process termination/response loss followed by read-only reconciliation; key loss/corruption/forget/restore and no backup transfer; old-binary denial; historical brightness restoration; visible unknown/missing-receipt results. These are not waived by pure-unit or fixture successes. Earlier unperformed M2/M3 checks remain separately open.
